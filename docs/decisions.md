# 확정 사항과 남은 정책

**v0.5 · 2026-11-05**. 이 대화에서 사용자가 확정한 요구사항을 우선한다. 아래 남은 질문은 해당 세부 동작의 제품 정책이며 이미 확정된 범위를 다시 승인받아야 한다는 의미가 아니다.

## 확정된 사항

- 각자 자기 경기만 기록하며 참가자·팀 점수·개별 득점자 연결·이벤트 수정 이력은 사용하지 않는다. #115에서 운동 원본의 goal/assist 발생 위치 배열은 보존한다.
- 쿼터별 골·어시스트 합계, 대표 포지션 하나, 운동 측정을 저장한다. 경기는 쿼터를 묶는 공통 정보다.
- 경기장 재사용을 유지한다. GPS·심박 측정 원본 전체를 서버에 저장한다.
- 운동 요약은 저장해 조회에 사용하며 경기 종료 집계/발행 대기 구조는 제거한다.
- 최고속도·평균속력·거리·칼로리·고강도 거리·가속/감속/방향전환 횟수·평균/최고 심박·Edwards TRIMP를 제공한다. TRIMP의 다른 모델과 Zone별 시간 저장은 사용하지 않는다.

- 서비스 시간대는 Asia/Seoul이다. 일반 API 날짜는 +09:00 포함 문자열, 운동 원본은 기존 Apple epoch 입력, DB 내부는 UTC 저장을 유지한다.

### P01 인증 상세

- Auth(#61·#72·#73) 응답 날짜와 공통 성공·오류 메타는 서울 `+09:00`으로 반환한다. Auth 내부 시각은 Instant를 우선하며 JDBC의 UTC LocalDateTime
  경계와 DATETIME(6)을 유지한다. 비Auth API와 일별 통계의 서울 기준은 이번 변경 대상이 아니다.

- 인증은 이메일 소유 확인과 비밀번호를 사용한다. Apple·Google 등 소셜 로그인은 현재
  범위에서 제외한다.
- 이메일은 앞뒤 공백 제거, IDNA 도메인 변환 및 전체 소문자화를 적용한다. `+`와 `.`은
  제거하지 않으며 `normalized_email`을 유일 식별자로 사용한다.
- 인증번호는 6자리, 3분 유효, 재발송 대기 60초다. 이메일별 최근 24시간 5회와 IP별
  최근 1분 3회 제한 중 하나라도 초과하면 차단한다. 실패는 재발송 후에도 최대 5회까지
  누적하며 재발송·성공 시 이전 코드는 무효화한다.
- registrationToken은 128비트 이상 opaque 비밀값으로, 원문 대신 해시를 저장한다.
  인증 이메일과 `SIGN_UP` 목적에 귀속하고 10분 유효·일회용으로 사용한다.
- 비밀번호는 8~64자이면서 UTF-8 72바이트 이하이며 문자 조합·연속 문자 규칙은 강제하지
  않는다. 로컬 상위 1,000개 차단 목록은 `Locale.ROOT` 소문자 기준으로 비교하고,
  BCrypt에는 입력 원문을 사용한다. HIBP 등
  외부 유출 비밀번호 API는 사용하지 않는다.
- Access Token은 15분의 Stateless JWT다. 보호 API마다 세션을 조회하지 않는다.
  Refresh Token은 최초 발급 기준 최대 90일이며 갱신마다
  Rotation한다. 이전 토큰 재사용 시 해당 세션만 폐기하고 다른 기기 세션은 유지한다.
- 로그인 실패는 미등록 이메일을 포함해 계정별 최근 15분 동안 집계하고, 10회부터 15분
  임시 제한한다. 성공 시 계정 실패 이력을 초기화하며 영구 계정 잠금은 사용하지 않는다.
  CAPTCHA와 로그인 IP별 실패 제한은 MVP 범위에서 제외한다.
- 비밀번호 재설정이 완료되면 현재 기기를 포함한 사용자 전체 Refresh 세션을 폐기하고
  재로그인을 요구한다. 기존 Access Token은 만료까지 최대 15분간 유효할 수 있다.
- Refresh(#62)는 Grace 없이 갱신하며 소비 토큰 재사용 시 해당 세션만 폐기한다. 정상 응답 유실·동시 요청도 재로그인이 필요할 수 있다. 소비 해시 이력은 세션 절대 만료까지 보존 후 정리한다.

#62 추가 승인(2026-11-06): 앱 내부 `@EnableScheduling`을 사용하고 시작 1시간 후부터 이전 정리 완료 기준 1시간 간격으로 실행한다. `expires_at <= UTC 현재 시각`만 삭제하며 실패는 기록 후 다음 주기에 재시도한다. 여러 인스턴스의 중복 삭제는 멱등적이지만 DB 잠금·공용 커넥션 풀의 성능 경합까지 제거하는 것은 아니다. 별도 배치 시스템은 도입하지 않는다.

- 운영 벤치마크에 따른 최종 BCrypt cost와 CAPTCHA·로그인 IP별 제한의 후속 도입 여부는 아직 미확정이다.

#63 승인 사항: 현재 또는 명시한 다른 본인 세션을 폐기한다. 타인·미존재 세션은 동일한 403,
이미 폐기된 본인 세션은 204다. 유효한 JWT는 로그아웃 이후에도 만료까지 최대 15분간
사용될 수 있다. Issue #63의 즉시 Access 무효화·현재 세션만 폐기 문구는 구 정책이며
Issue 본문은 이 작업에서 변경하지 않았다. 멱등 보존은 기존
`kiikick.match.idempotency-retention=P1D`의 **임시 재사용**이며 Auth 확정 정책이 아니다.
동일 로그아웃 범위·키에 한해 만료 기록을 재요청 시 제거한다. 미사용 기록의 물리적 일괄
정리는 후속 검토 대상이다. 새 테이블·Migration·Security 구조 변경은 없다.

#65 승인 사항: 내 프로필 GET/PATCH는 인증 Principal의 본인 UUID만 사용한다.
닉네임은 기존 CRUD·`VARCHAR(16)`을 유지하여 최대 16자(기존 Java 길이 검증)·중복 허용으로
적용하며 향후 P01/P07 정책 확정 시 재검토한다. 닉네임 UNIQUE·중복 검사는 추가하지 않는다.
온보딩 상태와 비교 동의는 기존 DB 값에서 파생하고 #66/#68 API는 구현하지 않는다.
기존 User CRUD는 보존하며 SELF 계약을 제공하는 `/users/me`로 클라이언트가 이행한다.
멱등 보존은 공통 P1D 설정 재사용이며 Auth 최종 보존 정책은 미확정이다.
Swagger/OpenAPI의 Auth 전체 문서화·`/v3/api-docs` 검증은 응답·정책 확정 후 별도 작업이다.

### P11 온보딩 동의 정책 (#59 승인 · #66 구현)

#66 코드·자동 테스트 및 사용자가 보고한 핵심 Swagger 수동 검증을 완료했다. #59의 탈퇴·보유·파기 세부 정리는 별도 변경으로 관리하며, 여기서는 온보딩에 필요한 확정 정책과 안내문만 반영한다.

**온보딩 동의 정책 승인: #59 / 구현·검증: #66 (2026-11-07)**

| purpose | policyVersion | 필수 여부 | 안내문 |
| --- | --- | --- | --- |
| GPS_COLLECTION | 1.0 | 선택 | 아래 GPS 수집·이용 안내문 |
| HEALTH_DATA | 1.0 | 선택 | 아래 건강정보 수집·이용 및 서버 저장 안내문 |

- #66에서는 위 두 목적만 처리한다. FRIEND_DISCOVERY는 후속 담당자 협의 대상으로 유지하며 FRIEND_COMPARISON을 검색 공개나 필수 동의로 대체하지 않는다.
- 둘 다 false이거나 consents가 빈 배열이어도 온보딩을 완료한다. 미제출 목적에는 동의 권한을 부여하지 않고, 제출된 항목만 true/false와 해당 버전·서버 기록 시각을 저장한다. consents 필드의 필수·null 불가 계약은 유지한다.
- 미지원 purpose 또는 policyVersion은 422 VALIDATION_FAILED로 거부하고 닉네임·동의 이력·온보딩 상태를 부분 저장하지 않는다. 기존 공통 검증 오류를 재사용한다.
- 목적별 1.0은 아래 실제 안내문에 대응한다. iOS는 해당 목적의 안내문을 표시하고 같은 버전을 전송해야 하며, 문구 변경 시 버전과 재동의 필요 여부를 함께 검토한다. 개인정보 처리방침 전체의 버전을 모든 목적에 자동 적용하지 않는다.
- 아래는 개인정보 처리방침 초안에 기반한 동의 안내문이다. #66의 이력 저장은 업로드 허용·철회·삭제 구현 완료를 뜻하지 않는다. 관련 기능의 운영 적용 여부는 별도로 검증한다.

**GPS 수집·이용 동의 안내문 — GPS_COLLECTION / 1.0 / 선택**

- 항목: 경기 중 위도·경도, 고도, 수평 위치 정확도, 이동 속도·방향 및 측정 시각.
- 목적: 경기 경로, 히트맵·타임라인 표시와 GPS 기반 거리·속도 등 본인의 운동 지표 계산 및 제공.
- 보유 기간: 해당 경기 기록 삭제, GPS 수집·이용 동의 철회 또는 회원 탈퇴 중 먼저 발생하는 때까지. 철회 시 해당 원본과 그 원본에 의존하는 요약·통계를 삭제하고 남은 동의 범위에서 계산 가능한 지표는 다시 산출합니다.
- 동의를 거부할 수 있으며 거부해도 계정 관리·수동 경기 기록은 이용할 수 있습니다. 다만 이동 경로·히트맵·구간 재생과 GPS 기반 분석은 제한됩니다. Apple 기기의 위치 권한과 이 동의는 별개입니다.

**건강정보 수집·이용 및 서버 저장 동의 안내문 — HEALTH_DATA / 1.0 / 선택**

- 항목: HealthKit 심박수·측정 시각, 운동 시작·종료 시각, 활동 칼로리, 누적 이동 거리 및 이용자가 별도로 설정하는 기준 최대 심박수.
- 목적: 본인의 심박 그래프, 운동 기록·부하 및 경기 분석 제공.
- 보유 기간: 해당 경기 기록 삭제, 건강정보 수집·이용 동의 철회 또는 회원 탈퇴 중 먼저 발생하는 때까지. 철회 시 해당 원본과 그 원본에 의존하는 요약·통계를 삭제하고 남은 동의 범위에서 계산 가능한 지표는 다시 산출합니다.
- 동의를 거부할 수 있으며 거부해도 계정 관리·수동 경기 기록은 이용할 수 있습니다. 다만 심박·건강정보 기반 운동 분석은 제한됩니다. Apple 기기의 HealthKit 권한, GPS 동의와 이 동의는 각각 별개입니다.

## 기술 계약과 구현 검토

- 사용자 입력인 합계/포지션과 센서에서 계산한 요약을 구분한다. 원본 전체를 GET에서 반복 계산하지 않는다.
- 동시 수정은 경기 행 잠금과 version/ETag를 재사용한다. 멱등 키와 센서 원본의 쿼터별 유일성은 별도로 관리한다.
- 운동 업로드 날짜는 Apple epoch 입력이며 서울 시각(+09:00) 응답·UTC 내부 저장과 구별한다. 임계값·누락 처리·계산 버전은 [계산 계약](dbdiagram/quarter-summary.md)에 기록한다.
- 요약의 PROCESSING 행을 복구 대상으로 사용한다. 별도 outbox 테이블을 도입하지 않는다. 워커·재시도/동기 계산 선택과 지연 목표는 구현 단계 검토다.
- 이 문서와 [API](api-spec.md), [ERD](erd.md), [SQL/DBML](dbdiagram/README.md)은 같은 개인·쿼터 모델을 사용한다. 명세를 실제 서버 계약으로 적용할 때 클라이언트 이행·마이그레이션·권한 검증이 별도로 필요하다.

## iOS 적용 협의

이미 확정된 요구사항과 아직 합의하지 않은 구현 방식을 [iOS 연동 협의표](api/ios-integration.md)에 구분했다. 업로드 If-Match 제거와 센서 경계 샘플 수신 방식은 개선 제안이며 현 API 계약에 자동 적용하지 않았다.

## 경기장 코너 보존 (#112 · 2026-11-09)

iOS가 보정한 cornerA~D를 그대로 보존하며 서버는 재보정하지 않는다. rawCornerA~D는 사용자 원본 핀으로 개별 nullable이며 연산에 사용하지 않는다. FieldCorner는 위도·경도 Double이다. 기존 좌표 없는 경기장은 유지하며 보정 코너 등록·수정 시 4개를 함께 받는다. 경기별 venueSnapshot의 과거 좌표 보존은 별도 범위다.

## 운동 원본 이벤트·경기장 사본 (#115 · 2026-11-09)

사용자 요청에 따라 events 배열의 goal/assist 및 location을 보존한다. field는 운동 당시 이름·보정 코너·원본 핀 사본이며 저장 경기장과 독립적이다. 이벤트를 별도 입력하는 goals/assists 합계에 자동 합산하지 않는다. 기존 클라이언트의 생략은 events=[], field=null로 처리하며 기존 원본 해시와 호환한다. JSON 컬럼은 운동 원본의 구성요소를 보존하는 용도이며 별도 이벤트 수정 API나 관계형 이벤트 이력은 추가하지 않는다.
