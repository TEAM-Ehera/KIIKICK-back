# 확정 사항과 남은 정책

**v0.4 · 2026-11-02**. 이 대화에서 사용자가 확정한 요구사항을 우선한다. 아래 남은 질문은 해당 세부 동작의 제품 정책이며 이미 확정된 범위를 다시 승인받아야 한다는 의미가 아니다.

## 확정된 사항

- 각자 자기 경기만 기록하며 참가자·팀 점수·개별 득점 이벤트·이벤트 이력은 사용하지 않는다.
- 쿼터별 골·어시스트 합계, 대표 포지션 하나, 운동 측정을 저장한다. 경기는 쿼터를 묶는 공통 정보다.
- 경기장 재사용을 유지한다. GPS·심박 측정 원본 전체를 서버에 저장한다.
- 운동 요약은 저장해 조회에 사용하며 경기 종료 집계/발행 대기 구조는 제거한다.
- 최고속도·평균속력·거리·칼로리·고강도 거리·가속/감속/방향전환 횟수·평균/최고 심박·Edwards TRIMP를 제공한다. TRIMP의 다른 모델과 Zone별 시간 저장은 사용하지 않는다.

- 서비스 시간대는 Asia/Seoul이다. 일반 API 날짜는 +09:00 포함 문자열, 운동 원본은 기존 Apple epoch 입력, DB 내부는 UTC 저장을 유지한다.

## 정책별 상태

| ID | 상태 | 남은 결정과 현재 기술 제안 |
| --- | --- | --- |
| P01 | 미확정 | 인증 제공자·가입 입력·온보딩 생략·토큰 수명. 기존 인증 API는 설계 초안 유지 |
| P02 | 개인 기록 확정, 비교 공개 범위 검토 | 경기/쿼터 원본은 본인만. 친구 비교는 관계와 양쪽 동의가 있는 분석 요약만 허용하는 제안. 공유 경기·기록자 양도는 범위 제외 |
| P03 | 쿼터 단위 확정 | 쿼터 수·설정 시간 상한, 장소/일시 필수 여부. 최소 준비 조건은 한 개 READY 쿼터라는 기술 초안 |
| P04 | 합계 입력 확정 | 쿼터별 본인 goals/assists를 0 이상 정수로 저장. 개별 골 발생·상대팀·자책골·득점자 연결은 모델링하지 않음 |
| P05 | 쿼터당 포지션 하나 확정 | 허용 포지션 코드, 입력 생략 여부. 초안은 미입력을 null로 표시하고 완료를 막지 않음 |
| P06 | 일부 미확정 | 경기 종료 후 직접 입력 기록 정정, 진행 경기 취소/재개. 초안에서는 보류. 센서 지연 업로드와 요약 계산은 종료 후에도 별도로 허용 |
| P07 | 미확정 | 친구 승인·거절·차단 정책과 검색 범위. 승인형 관계와 차단 시 관계 해제는 기술 제안 |
| P08 | 지표 목록·Edwards 확정, 산식 세부 미확정 | 고강도 심박 임계값, 주행 최소 속도, 가속/감속 임계값·지속·재진입, 방향전환 각도/저속 필터, GPS 품질, 누락 보간·심박 시간 가중, 평균속력 휴식 포함 여부. HRmax 출처와 갱신·초과 심박 처리, 기간 합계/비교 가능성도 검토. 미확정 지표는 null과 상태로 표시 |
| P09 | 미확정 | 알림 종류·트리거·수신 대상·보존. 타인의 경기 상세 접근을 알림으로 부여하지 않음 |
| P10 | 쿼터 측정·폰 경유 전송 확정 | 기존 Watch → iPhone 파일을 서버에 업로드. 쿼터당 원본 한 건은 기술 가정. 중단/재측정, 시계 오차·전송 지연, 파일 상한, 키 보존, 직접 서버 통신/오프라인 명령 큐 필요 범위는 미확정 |
| P11 | 원본 전체 저장 확정, 보존·삭제 미확정 | 수집 동의·목적, 위치/심박 보존 기간, 탈퇴 처리 기간·삭제 범위·로그 정책. 전체 저장은 영구 보존 확정을 뜻하지 않음 |
| P12 | 경기장 재사용 확정 | 개인 저장 목록과 장소 사본 유지. 외부 장소 검색 출처, 이름·주소 필수 여부·길이 검토 |

## 기술 계약과 구현 검토

- 사용자 입력인 합계/포지션과 센서에서 계산한 요약을 구분한다. 원본 전체를 GET에서 반복 계산하지 않는다.
- 동시 수정은 경기 행 잠금과 version/ETag를 재사용한다. 멱등 키와 센서 원본의 쿼터별 유일성은 별도로 관리한다.
- 운동 업로드 날짜는 Apple epoch 입력이며 서울 시각(+09:00) 응답·UTC 내부 저장과 구별한다. 임계값·누락 처리·계산 버전은 [계산 계약](dbdiagram/quarter-summary.md)에 기록한다.
- 요약의 PROCESSING 행을 복구 대상으로 사용한다. 별도 outbox 테이블을 도입하지 않는다. 워커·재시도/동기 계산 선택과 지연 목표는 구현 단계 검토다.
- 이 문서와 [API](api-spec.md), [ERD](erd.md), [SQL/DBML](dbdiagram/README.md)은 같은 개인·쿼터 모델을 사용한다. 명세를 실제 서버 계약으로 적용할 때 클라이언트 이행·마이그레이션·권한 검증이 별도로 필요하다.

## #12 구현 전 합의 항목

본인 소유 기록과 일반 API의 서울 시각, 운동 원본의 Apple epoch 계약은 위 확정 사항을 따른다. [내부 사용자 UUID 전달 방식](api/common.md#경기쿼터-인증-연결-계약-12)은 백엔드 서비스 경계로 채택한다. [담당 역할과 적용 순서](api/ios-integration.md#인증과-공통-응답-적용-순서-12)에 따라 백엔드가 계약과 구현을 먼저 제공하고 iOS가 연동한다. 아래 정책은 영향을 받는 작업별로 확인한다.

| 확인 시점 | 결정할 정책 |
| --- | --- |
| #16 경기 설정, #17 쿼터 설정, #18 경기 상태 전이 | P03/P12. #16에서 장소·일시 필수 여부, #17에서 쿼터 수·설정 시간 상한, #18에서 READY 최소 조건 확인 |
| #19 쿼터 완료, #21 포지션 저장 | P05. #19에서 미입력이 완료를 막는지, #21에서 허용 코드와 입력 생략 처리 확인 |
| #22 쿼터 운동 업로드 | P10. Watch/iPhone/서버 간 쿼터 ID 매핑, 마감·업로드 순서, 재측정, If-Match 적용 여부, 센서 경계·허용 오차와 파일 상한 확인 |

## iOS 적용 협의

이미 확정된 요구사항과 아직 합의하지 않은 구현 방식을 [iOS 연동 협의표](api/ios-integration.md)에 구분했다. 업로드 If-Match 제거와 센서 경계 샘플 수신 방식은 개선 제안이며 현 API 계약에 자동 적용하지 않았다.
